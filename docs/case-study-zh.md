# 案例复盘：Mac mini M4 + HDMI 显示器"睡眠唤醒后虚线"的完整诊断

> 时间：2026-09-26 ~ 09-27 · 环境：Mac mini M4（Mac16,10）、macOS 26.5.2、2018 年 2560×1440@60Hz 显示器、本机 HDMI 口直连

## 一、症状

- 显示器画面出现雪花状虚线/杂讯
- 拔插 HDMI 线可恢复；显示器待机唤醒或系统重启后复发
- 换线念头强烈（第一直觉都是线材问题）

## 二、排查 1：软件配置层（排除）

- `system_profiler SPDisplaysDataType`：2560×1440@60Hz，约 7Gbps 带宽需求——HDMI 1.4 线都够，**带宽不足假设直接出局**
- `ioreg` 确认走 `port-hdmi-1`；WindowServer 配置 8-bit、无 VRR、无缩放，配置层干净
- 电源日志确认症状与睡眠/唤醒循环相关

## 三、排查 2：热插拔对照实验（排除线材）

工具：`scripts/hotplug-monitor.sh`（内核日志流 + 每秒显示模式采样）。

用户物理拔插 4 次，内核级事件全部捕获：

| # | 拔线 | 插回 | 断开时长 | 链路重建 |
|---|---|---|---|---|
| 1 | 12:38:31.343 | 12:38:35.823 | 4.5s | 0.3s ✅ |
| 2 | 12:38:42.145 | 12:38:42.637 | 0.5s | 0.3s ✅ |
| 3 | 12:38:57.490 | 12:39:04.213 | 6.7s | 0.3s ✅ |
| 4 | 12:39:08.281 | 12:39:09.009 | 0.7s | 0.3s ✅ |

每次重建事件链完整且零错误：

```
HDMI_HPD interrupt (hpdState=1)
→ plug_gated: display HPD asserted
→ serviceNotificationAnalyticsEDID published
→ Display 3 hot plug 1
→ hotplug-state 1 updating digital modes
→ 42 timing modes, 14 color modes
→ 恢复 2560x1440@60
```

**4/4 全部 0.3 秒完美重建，无重试、无模式缺失。线材/接口质量实测无罪。**

排错花絮：采样日志中的 1920×1080 记录曾误判为"重插后降级点亮"。实际是 macOS 在主显示断开期间对 `CGDisplayCopyDisplayMode` 返回的 fallback 值（窗口与拔线时段完全吻合）。做采样工具时要注意这个坑。

## 四、排查 3：FreeSync A/B 对照（锁定根因）

显示器 OSD 无深度睡眠选项，仅有 FreeSync/Adaptive Sync（**开启**）与 DP 版本 1.1。

实验设计（关键：停掉自动修复守护，保证纯净对照）：

1. 杀掉 `display-resync --watch` 守护
2. OSD 关闭 FreeSync
3. `pmset displaysleepnow` 强制显示器深待机
4. 待机约 50 秒后用户唤醒

结果：**无虚线，干净恢复**（`powerd` 日志确认 Did Wake 事件正常，无任何显示错误）。

## 五、根因机制

- 60Hz 固定刷新率场景下 macOS 不输出 VRR，FreeSync 毫无用处
- 但显示器端 FreeSync 开启会让每次 HDMI 握手协商多一层 Adaptive-Sync 信息帧
- 双方同时从深睡唤醒时，该协商状态机容易卡进半锁定状态 → 虚线
- 这完美解释症状的不对称性：清醒状态热插拔秒恢复（协商简单），深睡唤醒才出错（协商复杂）

## 六、最终方案

1. **FreeSync 保持关闭**（根治，免费）
2. `display-resync --watch` 守护兜底：唤醒后 2.5 秒自动切分辨率重同步（保险）

## 七、经验总结

1. **"重插就好" ≠ 线材问题**——重插的本质是强制重新握手，握手问题也可能出在协商层而非物理层
2. **对照实验要控制变量**：验证 FreeSync 前先停掉自动修复守护，否则唤醒被自动修好，实验白做
3. **症状的分布是最大的线索**：只在唤醒后出现 vs 只在移动线缆后出现，指向完全不同的层
4. **别信采样工具的表面输出**：1080p"降级"其实是 API 的 fallback 值
5. 环境坑：macOS 26 日志隐私化（EDID 拉不到）、部分机器 launchctl 拒绝一切新用户服务（error 5）——诊断工具要做好降级路径

## 八、后续追踪（2026-09-28）：根治结论修正为"分场景"

关闭 FreeSync 的次日，系统级睡眠唤醒后虚线复发（重插多次才恢复）——首次复发没有盲修，而是先取证：

**关键差异：两条不同的唤醒路径**

| 场景 | GPU 状态 | FreeSync 关闭后 |
|---|---|---|
| 显示器待机唤醒（`pmset displaysleepnow`，系统不睡） | 保持活动，只有显示器端重新锁定 | ✅ 干净恢复 |
| **系统级睡眠唤醒**（整机 Deep Idle，如合盖/节能睡眠） | **断开链路，唤醒时全链路重建** | ❌ 仍复发（数据点：[issue #1](https://github.com/lcx0cd/mac-hdmi-freesync-fix/issues/1)） |

**结论修正**：FreeSync 是"显示器待机"场景的根因；系统睡眠唤醒还存在第二层问题（可能是 GPU 全链路重建时序问题），FreeSync 关不掉它。原 A/B 实验只覆盖了前者。

**工具同步升级**：复发时发现旧版守护日志被重定向到 /dev/null，无法确认它是否开火——已改为进程自带文件日志（启动/唤醒检测/重同步结果，全部带时间戳写 `~/.workbuddy/logs/display-resync.log`），不依赖 stdout 重定向。

**方法论教训**：
- "根治"结论要写明覆盖的**场景边界**，超出边界的场景需要重新验证
- 偶发问题的每次复发都是宝贵的取证机会——复发时**先看日志再动手**
- 可观测性不是可选优化：守护类工具必须有自带的、不依赖重定向的日志
